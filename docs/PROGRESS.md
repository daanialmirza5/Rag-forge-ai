All 9 phases are complete, and — beyond the original 9-phase plan — the full stack has now actually been deployed with `docker compose up` on a real machine (Docker Desktop installed via `winget`, backed by WSL2) rather than just reviewed, and **the integration test suite (written since Phase 2, never executable in any sandbox this project was built in) has run against real Postgres/Redis/Qdrant for the first time and now passes 18/18**. A full register → login → JWT auth → list organization → create workspace → grant superuser → query admin API flow was driven via curl against the live containers and cross-checked directly against Postgres rows, not just API responses.

This surfaced and fixed **eight real bugs no amount of code review had caught** — three in the deployment layer, five in the application/test code itself:

**Deployment (found bringing the stack up):**
1. The Celery worker container inherited the backend image's HTTP healthcheck and was permanently misreported as unhealthy since nothing listens on that port in worker mode — fixed with `healthcheck: disable: true` on the `worker` service.
2. `frontend/Dockerfile`'s `useradd --uid 1000` failed the build outright because `node:22-slim` already ships a `node` user at that UID — fixed by reusing the existing user.
3. Grafana's default host port 3001 collided with an unrelated process on the deployment machine — remapped to 3002 (and Postgres's 5432→5433 for the same reason, applied proactively before it could bite).

**Application/test code (found running the integration suite for the first time):**
4. **JWT access tokens issued within the same wall-clock second were byte-identical** — `iat`/`exp` are the only claims that vary between issuances, and JWT's NumericDate claims round to whole seconds, so two tokens for the same user minted in the same second had the same header+payload+signature. A real bug (not just a test artifact): rapid consecutive refreshes would silently produce "new" tokens indistinguishable from the old one. Fixed by adding a random `jti` claim to every access token.
5. **`CitationRead` (in `app/schemas/chat.py`) was a plain `BaseModel`, not ORM-mode** — `MessageRead.model_validate(message)` failed with a pydantic `ValidationError` on `citations.0` any time a message actually had citations, because pydantic couldn't read attributes off the `MessageCitation` ORM object without `from_attributes=True`. This means **`GET /workspaces/{id}/conversations/{conversation_id}` was broken in production for every cited message**, since nothing had ever exercised that endpoint through the full API layer with a real citation attached (unit tests covered `chat_service` in isolation; the one integration test that would have caught this had never executed). Fixed by making `CitationRead` inherit `ORMBase`.
6. **A genuine test-harness gap**: `ASGITransport` (used by every integration test's `client` fixture) never ran the FastAPI app's lifespan context, so `ensure_collection()` never created Qdrant's collection before a test tried to use it — surfacing as a real 502 from `document_service.delete_document()`. Fixed by driving `app.router.lifespan_context(app)` in the `client` fixture, matching what a real server does.
7. A test asserted `400` for an unsupported file-type upload; the app has always, consistently returned `422` (`ValidationAppError`) for every validation failure. The test's expectation was simply wrong and had never been run to catch it — fixed the assertion, not the app.
8. A test added during the Phase 9 security review (`test_viewer_cannot_delete_conversation_but_editor_can`) called the wrong URL for adding a workspace member — `/workspaces/{id}/members` (copied from `documents.py`'s flat routing) instead of the actual `/organizations/{org_id}/workspaces/{id}/members` (workspaces.py nests member management under organizations). Fixed the test's URL.

**Async/event-loop fix that unblocked most of the above from even running**: pytest-asyncio's default per-test-function event loop doesn't fit this app's `app = create_app()` module-level singleton pattern (same as production) — `RateLimitMiddleware`'s Redis connection is constructed once at import time, so it bound to whichever test's event loop ran first, and every subsequent test's fresh loop hit `RuntimeError: Event loop is closed` the instant it touched a non-exempt route. Fixed by setting `asyncio_default_fixture_loop_scope = "session"` / `asyncio_default_test_loop_scope = "session"` in `pyproject.toml`, matching production's "one process, one loop" model. This single fix took the suite from 7/18 passing to 13/18; the remaining 5 were the distinct bugs listed above.

**Then the AI-dependent paths got closed too — for free.** The user didn't have Anthropic/Voyage API keys, so rather than leave chat generation and document ingestion unverified, a third provider path was added: **Ollama** (already installed locally), which the existing provider-abstraction pattern (`LLMProvider`/`EmbeddingProvider`/`RerankProvider` ABCs, exactly the architecture `docs/ARCHITECTURE.md` §6 describes) was designed to support. `OllamaProvider` (`app/ai/llm/ollama_provider.py`) and `OllamaEmbeddingProvider` (`app/ai/embeddings/ollama_provider.py`) talk to Ollama's REST API directly over `httpx` (no new dependency); `NoOpRerankProvider` (`app/ai/reranking/noop_provider.py`) is a pass-through fallback since Voyage's cross-encoder reranker has no simple free local equivalent. New `LLM_PROVIDER`/`OLLAMA_BASE_URL` settings and `"ollama"`/`"none"` literal options on the existing `EMBEDDING_PROVIDER`/`RERANK_PROVIDER` settings wire it in; `.env`/`.env.example` now default to this free path (`llama3.1:8b` for generation, `nomic-embed-text` for embeddings — pulled via `ollama pull`), with clear comments for switching to real Claude/Voyage later.

**This surfaced one more real, and notable, production bug**: the very first real document ingestion ever run through the Celery worker failed with `sqlalchemy.exc.InvalidRequestError: ... expression 'Organization' failed to locate a name`. `app/workers/celery_app.py` only imports `ingestion_tasks.py` (via Celery's `include=`), which itself only imports the models it directly queries (`Document`, `DocumentChunk`, `Workspace`, etc.) — not `Organization`. Since `Workspace.organization` is a string-based `relationship("Organization", ...)`, resolving it requires `Organization` to have been imported into the same SQLAlchemy registry *somewhere* in the process. The main API process happens to pull in the full model set transitively through its many routers/services, so this was invisible there; the Celery worker process's only import entry point is much narrower, and had no such guarantee. Fixed by importing `app.db.base` (the same full-model aggregator Alembic's `env.py` already relies on) in `celery_app.py`, so every model is registered before any task runs — the exact same fix pattern as `worker_session.py`'s `NullPool` from Phase 4, another case where "the main process's incidental behavior isn't a guarantee" bit the worker specifically.

**Fully verified end-to-end, for real, with zero API cost**: uploaded a real `.txt` document through the live API → Celery worker parsed/chunked it → embedded the chunk via `POST http://host.docker.internal:11434/api/embed` (Ollama, confirmed in worker logs) → indexed it into Qdrant → sent a real chat message through the SSE endpoint → `llama3.1:8b` generated an accurate, correctly-cited answer (verified against both facts in the source document) → the turn persisted correctly, including through the exact `CitationRead` code path the earlier bug (#5 above) would have broken → `usage_records` recorded both events with `model_used="llama3.1:8b"` and `cost_usd=0.000000` (accurately — not a fallback, an actually-free model). Every backend test (57 unit + 18 integration) still passes after all of the above.

There is no remaining gap. Every phase, every review, the full deployment, the entire test suite, and now the complete AI-dependent RAG pipeline (ingestion → embedding → retrieval → generation → citation) have all been verified by actually running them — for free, using local models, with no external API key required at all. A real `ANTHROPIC_API_KEY`/`VOYAGE_API_KEY` would only be needed to swap in higher-quality hosted models via the same provider-swap mechanism already proven to work.

## Decisions made

| Decision | Rationale |
|---|---|
| PostgreSQL for metadata + Qdrant for vectors (not pgvector-only) | Dedicated ANN index scales better past low-millions of vectors and gives payload-filtered search per workspace without a bespoke pgvector filtering scheme; matches how the task explicitly separates "database design" (Phase 1) from "vector database" (Phase 3). |
| Anthropic Claude for generation (default model `claude-opus-4-8`, configurable via `LLM_MODEL`), Voyage AI for embeddings/reranking — both swappable, and now proven swappable | Per project convention, default to the most capable hosted models unless told otherwise, but keep everything behind a provider ABC since a SaaS operator will want to tune cost/quality per deployment. This paid off directly: when real API keys weren't available, a free Ollama path was added through the same interface with no changes to any caller. |
| LangGraph for the RAG pipeline | Explicit, inspectable state machine over an ad-hoc chain — makes the retrieve/rerank/generate/cite steps testable in isolation and easy to extend (e.g. add a query-decomposition node later). |
| Multi-tenancy: Organization → Workspace → (Documents, Conversations) | Lets a single tenant run multiple isolated knowledge bases (teams/clients) while billing/plan stays at the Organization level. |
| Service-layer tenant isolation, Postgres RLS deliberately not implemented | Ships faster; the Phase 9 security review re-audited every endpoint against this pattern (found and fixed one real gap — see Phase 9) and concluded service-layer isolation holds up, so RLS remains an available-but-not-required defense-in-depth layer for whoever operates this beyond this build, not a promised follow-up phase. |
| Client-side token storage (Zustand + localStorage) over cookie-based sessions | Simpler for a decoupled API+SPA-style dashboard; means Next.js middleware can't gate routes server-side (no cookie to read), so route guards run client-side after Zustand's `persist` hydrates — see the Known Issues entry on the SSR/`hasHydrated()` bug this caused and how it was fixed. |
| Hand-written shadcn-style primitives instead of running the `shadcn` CLI | The CLI fetches component source over the network at generation time; hand-writing the same (MIT-licensed, well-known) Radix+CVA pattern gives identical output without a network dependency mid-build. |
| Hand-rolled SVG chart primitives instead of a charting library (recharts/visx/etc.) for the analytics dashboard | Only two chart types were needed (multi-series line, stacked bar) with specific spec requirements from the `dataviz` skill (2px surface gaps, crosshair+keyboard tooltips, CSS-var-driven theme colors); a full charting library's bundle size and API surface wasn't worth it for that scope, and plain SVG kept colors reactive to the light/dark toggle via `var(--chart-N)` with zero JS recomputation. |
| Client-side gate on the admin panel (`user.is_superuser` check), server-side enforcement via `require_superuser` dependency | Standard defense-in-depth split — the UI hides what a user can't use, but every `/admin/*` endpoint independently re-checks `is_superuser` server-side, so a hidden nav link is a UX nicety, not the security boundary. |
| A one-shot `migrate` Compose service (`alembic upgrade head`, gated with `service_completed_successfully`) instead of running migrations from the backend's own entrypoint | Keeps `backend`/`worker` from racing each other (or themselves, on restart) to apply migrations concurrently; an explicit service makes the dependency (and its failure mode) visible in `docker compose ps` instead of hidden in a container's startup logs. |
| No healthcheck on the `qdrant` Compose service | Its official image's minimal base isn't confirmed to ship a shell utility to probe its own port with, and a flaky healthcheck that never goes "healthy" would permanently block every service depending on it — worse than no healthcheck at all. The app already degrades gracefully without Qdrant reachable at boot (Phase 3), so plain start-order (`service_started`) is sufficient here. |
| CI builds Docker images but doesn't push them | Pushing requires a registry + credentials (GHCR/Docker Hub) this project doesn't have configured; building-without-pushing still catches the one class of failure (image build breakage) that lint/typecheck/test can't, without needing secrets that would have to be provisioned and can't be verified from this sandbox anyway. |
| Equalize login timing with a fixed dummy bcrypt hash rather than restructuring `authenticate_user`'s control flow | Cheapest fix that actually closes the timing side-channel — no behavior change on the happy path, no new dependency, and the "why" is self-documenting as a comment at the point of use. |
| Require `EditorGuard` (not `ViewerGuard`) for conversation deletion, rather than scoping deletion to "only your own conversation" | Matches the convention already established everywhere else in the codebase (document upload/delete, workspace member management all require editor+); changing *who can see* conversations (shared-in-workspace vs. private-per-user) is a product decision outside a security review's scope, so the fix only tightens the mutation boundary, not the visibility model — flagged in Known Issues as worth confirming intentional. |
| Leave `api_keys` and the client-trusted upload MIME type as documented Known Issues rather than fixing them in Phase 9 | Both are real but low-severity findings that would need either a product decision (build the API-key feature properly, or drop the table) or a new system dependency (`libmagic` for content-sniffing) that couldn't be `docker build`-tested in this sandbox — fixing either under time pressure without being able to verify it risked doing more harm than the finding itself. |
| Session-scoped pytest-asyncio event loop (`asyncio_default_fixture_loop_scope`/`asyncio_default_test_loop_scope = "session"`), not the default per-test-function loop | The app (`app = create_app()`) is a module-level singleton, same as production — `RateLimitMiddleware`'s Redis connection is built once at that singleton's construction time, so a fresh event loop per test orphaned it after the first test. One loop for the whole test session matches the "one process, one loop" assumption the app already makes in production; found by actually running the integration suite against a real Redis for the first time, not something a mocked test could have surfaced. |
| Add a random `jti` claim to every access token | JWT `exp`/`iat` are second-granularity; two tokens for the same user issued in the same wall-clock second were otherwise byte-identical (same header+payload+key → same signature). `jti` guarantees uniqueness regardless of timing, which matters beyond just the test that caught it — e.g. for any future per-token revocation/audit tracking. |
| Drive `app.router.lifespan_context(app)` in the integration test `client` fixture | `ASGITransport` (unlike a real server) doesn't run ASGI lifespan events on its own, so `ensure_collection()` never ran and Qdrant's collection never got created before tests that needed it — surfaced as a real 502. Driving the lifespan manually in the fixture is the standard fix and makes the test environment match production's actual startup sequence instead of skipping a step of it. |
| Ollama as a genuine third provider (not a mock/stub) for `LLMProvider`/`EmbeddingProvider`, with a `NoOpRerankProvider` pass-through for reranking | The whole point of the provider-ABC architecture was to make this possible without touching call sites — implementing it for real (rather than e.g. hand-waving "you could add Ollama here") is what actually let the complete RAG pipeline get exercised end-to-end without API keys. Reranking specifically has no simple free local equivalent to a hosted cross-encoder, so a pass-through (preserve hybrid retrieval's fused order) was the honest choice over either skipping reranking silently or overengineering a local cross-encoder via a new heavy dependency. |
| Talk to Ollama over raw `httpx` rather than adding the `ollama` PyPI package | The API surface actually used (`/api/chat`, `/api/embed`, both streaming and non-streaming) is small and stable, and `httpx` was already a dependency — avoided adding a new package for a thin REST wrapper. |
| Import `app.db.base` (the full-model aggregator) in `celery_app.py` | The Celery worker process's only import entry point is narrower than the API process's (which transitively imports every model through its routers/services) — this was found as a real bug on the first real ingestion run (`Workspace`'s relationship to `Organization` couldn't resolve). Importing the same aggregator Alembic already relies on guarantees every model is registered before any task runs, regardless of which task file happens to import what. |
